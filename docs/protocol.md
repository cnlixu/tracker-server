# 电力定位跟踪器 JT/T 808-2019 接入规范

本项目只接受 JT/T 808-2019 二进制协议，不再兼容 `$PTRK` ASCII 或原自定义 HEX 协议。传输层固定使用 TCP。

## 1. 裁剪后的消息集合

| 方向 | 消息 ID | 用途 |
| --- | ---: | --- |
| 终端→平台 | `0x0100` | 首次注册，获取鉴权码 |
| 平台→终端 | `0x8100` | 注册应答 |
| 终端→平台 | `0x0102` | 每次 TCP 连接建立后的鉴权 |
| 终端→平台 | `0x0200` | 单条实时位置上报 |
| 终端→平台 | `0x0704` | 离线位置批量补传 |
| 平台→终端 | `0x8001` | 鉴权、位置和批量位置的通用应答 |
| 平台→终端 | `0x8103` | 设置完整的版本化项目参数 |
| 平台→终端 | `0x8104` / `0x8106` | 查询全部／指定终端参数 |
| 终端→平台 | `0x0104` | 查询参数应答 |
| 终端→平台 | `0x0001` | 参数设置通用应答 |

心跳、区域路线、电话、文本、多媒体、驾驶员卡、CAN 等消息不属于本产品。设备每轮上传后主动休眠，TCP 连接不是常驻连接，因此不发送 `0x0002` 心跳。

## 2. 标准帧

- 起止标识：`0x7E`。
- 2019 版协议版本号：`0x01`，消息体属性 bit14 必须为 1。
- 终端手机号：10 字节 BCD，使用 SIM 对应的真实号码，不允许用 IMEI、IMSI 或 ICCID 替代。不足 20 位时左补零。手机号与固定 SIM 的 ICCID 在产线通过 USB 用户虚拟串口写入终端 FSKV；终端每次启动校验 ICCID，换卡后不得沿用原手机号和鉴权码。
- 多字节整数：大端序。
- 校验：消息头到消息体末字节逐字节 XOR。
- 转义顺序：`0x7D → 0x7D 0x01`，`0x7E → 0x7D 0x02`。
- 单个物理帧消息体最多 1023 字节；超出后使用 JT/T 808 标准分包头。

TCP 是字节流，服务端必须按 `0x7E` 持续拆帧，支持半包、粘包、连续多帧和转义字符，不能把一次 `read()` 当成一帧。

平台下行消息流水号由服务进程统一分配，按 16 位无符号数逐条递增并允许回绕，禁止固定写成 `0`。终端应答必须回显对应的平台流水号和消息 ID；流水号只用于当前交互关联，不承担全局数据去重。

## 3. 注册和鉴权

### 3.1 终端身份及产线写入

生产设备档案应保存终端手机号、ICCID和IMEI三项身份。例如：

| 字段 | 示例 | 要求 |
| --- | --- | --- |
| 终端手机号（MSISDN） | `18508225213` | 必须是当前SIM对应的真实号码，作为JT/T 808终端号 |
| ICCID | `89860064221642652497` | 由设备从SIM自动读取，用于锁卡校验 |
| IMEI | `862288087606784` | 由Air780自动读取，在首次成功鉴权时与终端号绑定 |

手机号必须真实归属于该ICCID。设备无法从运营商网络反查两者的对应关系，只能保证运行时插入的SIM与写号时ICCID一致，所以产线管理系统应负责校验并保存正确映射。服务器以终端手机号为注册主键，以IMEI为唯一设备约束；错误号码或重复号码会造成设备归属错误或鉴权失败。

本项目的 `0x0100` 使用下述 EPTR 项目注册体，会同时上传 ICCID 和 IMEI；平台仍应保存产线确认过的手机号、ICCID、IMEI 对应关系。终端本地锁卡校验和平台档案校验承担不同职责，不能互相替代。

设备开机后在USB用户虚拟串口 `uart.VUART_0` 开放60秒写号窗口，串口参数为 `115200、8N1`，使用CRLF结尾。产线依次发送：

```text
AT
AT+PHONE=18508225213
```

成功响应：

```text
+PHONE:OK,18508225213,89860064221642652497
OK
```

设备随后自动重启。重启后可发送 `AT+PHONE?` 复核，正确响应为：

```text
+PHONE:18508225213,89860064221642652497
OK
```

写号命令会自动读取ICCID、持久化手机号与ICCID并删除旧鉴权码。服务器不需要人工录入明文鉴权码；设备下一次建立上传连接时重新执行标准注册和鉴权流程。

### 3.2 注册及鉴权流程

设备无本地鉴权码时发送 `0x0100`。测试服务器为本次注册生成独立随机鉴权码，将其 SHA-256 摘要和终端号持久化后，通过成功 `0x8100` 返回明文鉴权码；设备将鉴权码保存到 FSKV。终端重复注册会签发新鉴权码并使旧码失效。

每次 TCP 连接建立后，设备必须先发送 `0x0102`。平台按消息头终端手机号查找注册凭据，校验鉴权码，并在首次成功鉴权时绑定鉴权体内的 15 位 IMEI。终端手机号与 IMEI 是不同字段，不要求数值相同。平台返回成功 `0x8001` 后才允许位置上报。

测试服务器和量产平台都必须为每台设备分配独立鉴权凭据，不能让所有设备共用固定鉴权码。

### 3.3 EPTR 项目注册消息体

消息 ID、2019 版消息头、转义和校验仍完全使用 JT/T 808；仅 `0x0100` 消息体按电力定位跟踪器业务裁剪。固定区如下：

| 偏移 | 长度 | 字段 | 说明 |
| ---: | ---: | --- | --- |
| 0 | 2 | 省域 ID | `WORD` |
| 2 | 2 | 市县域 ID | `WORD` |
| 4 | 11 | 制造商 ID | UTF-8/ASCII，右补零 |
| 15 | 4 | profile_magic | 固定 `EPTR` |
| 19 | 1 | profile_version | 当前为 `1` |
| 20 | 1 | terminal_type | 终端类型 |
| 21 | 4 | capabilities | 能力位图 |
| 25 | 4 | report_interval_sec | 唯一的定位/上报周期，秒 |
| 29 | 1 | TLV 数量 | 后续注册附加项个数 |

注册 TLV 使用 `ID BYTE + 长度 BYTE + 值`：`0x01` 服务点 ID、`0x02` 资产 ID、`0x03` 型号、`0x04` SN、`0x05` IMEI、`0x06` ICCID、`0x07` 硬件版本、`0x08` 软件版本、`0x09` 组织编码、`0x0A` 生产批次、`0x0B` 当前配置版本（`DWORD`）。除配置版本外均为 UTF-8 字节串。

## 4. 参数配置与 PSM+ 下发

平台通过管理 API `GET/PUT /api/devices/{imei}/configuration` 维护每台终端的期望配置。可变项包括省域 ID、市县域 ID、终端类型、上报周期、服务点 ID、资产 ID 和组织编码；制造商、能力、型号、SN、IMEI、ICCID、软硬件版本、生产批次属于设备事实，不通过参数下发修改。

参数 ID：

| 参数 ID | 类型 | 含义 |
| ---: | --- | --- |
| `0x00000029` | `DWORD` | 上报周期（秒） |
| `0x0000F100` | `DWORD` | 配置版本，整组设置必须携带 |
| `0x0000F101` | `WORD` | 省域 ID |
| `0x0000F102` | `WORD` | 市县域 ID |
| `0x0000F103` | `BYTE` | 终端类型 |
| `0x0000F104` | UTF-8 | 服务点 ID |
| `0x0000F105` | UTF-8 | 资产 ID |
| `0x0000F106` | UTF-8 | 组织编码 |

设备在 PSM+ 期间不可达，因此平台不主动建立连接。管理端更新后将配置标为 `pending`；设备下次主动连接并完成 `0x0102` 鉴权后，平台立即发送完整 `0x8103`。终端校验整组参数和版本，将其作为一个带 CRC 的 FSKV 对象写入成功后才返回 `0x0001` 成功。平台用“平台下行流水号 + 被应答消息 ID + 配置版本”匹配应答，成功后才推进 `applied_revision`；断线、超时或失败会在下次连接重发同一版本。

版本小于终端当前版本时拒绝；版本相同且内容一致时幂等成功；版本相同但内容不同则拒绝。修改配置不会要求终端重新注册或重新签发鉴权码。

## 5. 位置信息

`0x0200` 的前 28 字节完全使用 JT/T 808-2019 标准位置基本信息：报警标志、状态、纬度、经度、高程、速度、方向和 GMT+8 BCD 时间。

标准附加项：

| ID | 长度 | 内容 |
| ---: | ---: | --- |
| `0x30` | 1 | 蜂窝网络信号强度，当前为 CSQ 0～31 |
| `0x31` | 1 | 参与定位的卫星数 |

本产品自定义附加项位于标准允许的 `0xE0～0xFF` 范围：

### 0xE0：可靠记录身份

长度固定 10 字节：

| 偏移 | 长度 | 字段 | 说明 |
| ---: | ---: | --- | --- |
| 0 | 1 | version | 当前为 `1` |
| 1 | 4 | generation_id | 设备数据代次，uint32 |
| 5 | 4 | record_seq | 代次内单调记录序号，uint32 |
| 9 | 1 | flags | bit0 时间可信；bit1～3 唤醒原因 |

数据库唯一键必须是 `(terminal_id, generation_id, record_seq)`。JT/T 808 的 16 位消息流水号只用于请求/应答关联，会循环，不能作为全局去重键。

### 0xE1：电池信息

长度固定 3 字节：

| 偏移 | 长度 | 字段 | 说明 |
| ---: | ---: | --- | --- |
| 0 | 2 | battery_mv | VBAT 毫伏值；`0` 表示未知 |
| 2 | 1 | battery_percent | 0～100；`0xFF` 表示未知 |

电量百分比由终端根据可配置锂电池曲线估算。终端先对多次 ADC 采样取中值，再进行低通和迟滞处理；平台应同时保存毫伏值与百分比，不应使用百分比反推原始电压。

### 0xE2：HDOP

长度固定 1 字节，单位为 0.1；`0xFF` 表示未知。

## 6. 批量补传

离线记录使用标准 `0x0704`：

1. 数据项个数 `WORD`，范围 1～512。
2. 位置数据类型 `BYTE`，离线缓存使用 `1`（盲区补报）。
3. 每条记录为 `位置汇报数据体长度 WORD + 0x0200 消息体`。

512 条记录会形成一个逻辑 `0x0704` 消息，再按 1023 字节上限拆成多个标准子包。服务端必须按终端号、消息 ID、消息流水号、总包数和包序号重组，完整校验并解析整批后再入库。

当前 TCP 模式不启用 `0x8003` 补包请求：任何子包缺失都会导致本次请求没有成功应答，设备超时后原样重发整批。

## 7. ACK 与可靠性

平台仅在以下动作全部完成后返回成功 `0x8001`：

1. 完整接收并重组逻辑消息。
2. 校验所有物理帧和位置记录。
3. 使用记录唯一键幂等写入全部轨迹点。
4. 更新设备最新状态。
5. 提交数据库事务。

`0x8001` 必须回显终端消息流水号和消息 ID。结果码采用标准定义：`0` 成功、`1` 失败、`2` 消息有误、`3` 不支持、`4` 报警处理确认。

设备只有收到与当前请求流水号和消息 ID 完全匹配的成功应答，才从 Flash 循环队列删除对应记录。ACK 丢失时设备会重传；平台遇到重复记录仍应幂等提交并返回成功。

校验失败或无法信任消息头时不返回 ACK，让终端超时重传。数据库失败返回结果 `1`，消息体错误返回结果 `2`。

## 8. 数据单位

- 坐标：WGS-84，线上单位 `10^-6` 度。
- 高程：米。
- 速度：线上单位 `0.1 km/h`；当前数据库兼容字段仍存储节。
- 方向：0～359 度。
- 时间：JT/T 808 线上为 GMT+8，服务器解析后统一存 UTC。
- VBAT：mV。
- HDOP：0.1。

## 9. 安全边界

JT/T 808 的 XOR 只能检错，不能提供加密、服务器身份认证或防伪造。正式部署应在 JT/T 808 之外启用 TLS，并使用每设备独立鉴权码；敏感定位数据在数据库和备份中也应加密并实施访问审计。
